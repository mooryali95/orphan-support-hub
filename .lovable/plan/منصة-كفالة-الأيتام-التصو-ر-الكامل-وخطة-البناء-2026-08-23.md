# منصة كفالة الأيتام — التصوّر الكامل وخطة البناء

القرار: **لا نبدأ من الصفر**. ننقل معمار منصة «مهر» المرفوع (TanStack Start + Lovable Cloud + أدوار + RLS + بريد + مراقبة) كأساس، ونعيد تشكيل الكيانات لمجال اليتيم. المكوّنات العامة (الهيكل، الصلاحيات، الطلبات متعددة الخطوات، خزنة المستندات، البريد المعاملاتي، لوحة الإدارة، المراقبة والتنبيهات) تُعاد بنسبة كبيرة؛ منطق «المهر/الوظائف» يُستبدل بمنطق «الاحتياج/الكفالة».

## الأدوار الأربعة

- **ولي الأمر / اليتيم**: إنشاء ملف اليتيم، رفع المستندات، تتبّع حالة الاعتماد والكفالة والتقارير.
- **جهة الرعاية (جمعية/دار)**: ترفع وتوثّق ملفات الأيتام تحت إشرافها، تحدّد الاحتياجات، ترفع تقارير دورية وإيصالات الصرف.
- **الكافل / الداعم**: يتصفّح البروفايلات المعتمدة (مجهولة الهوية جزئياً)، يفتح كفالة شهرية أو دعم لمرة واحدة، يتابع أثر دعمه.
- **الإدارة (مهر/المشغّل)**: اعتماد الملفات والجهات، المطابقة، مراجعة التقارير، الصرف والتدقيق، الملاحظة والتنبيهات.

## رحلة النظام من البداية للكفالة

```text
جهة رعاية/ولي أمر → إنشاء ملف يتيم (7 خطوات) → مستندات وتوثيق
      → مراجعة الإدارة → اعتماد → نشر البروفايل في الدليل
كافل → تسجيل → تحقق → تصفح/فلترة → اختيار يتيم → اختيار نوع الكفالة والمبلغ
      → دفع إلكتروني (أول دفعة + اشتراك شهري) → عقد كفالة نشط
جهة الرعاية → تقارير دورية (تعليم/صحة/معيشة) + إيصالات
الإدارة → تسوية وصرف → تدقيق → إشعارات للكافل → تجديد/إيقاف
```

خطوات ملف اليتيم: (1) بيانات أساسية (2) الوصاية والجهة (3) الوضع الأسري والمعيشي (4) التعليم (5) الصحة (6) الاحتياجات وحساب المبلغ الشهري المقترح (7) المستندات والإقرار.

## نموذج البيانات (جداول جديدة على نفس أنماط مهر)

- `orphans` — الملف الأساسي + حالة (draft/submitted/under_review/approved/rejected/sponsored/archived) + حقول عامة مقابل حقول حسّاسة.
- `guardians` و`care_organizations` — الأولياء والجهات + حالة اعتماد الجهة.
- `orphan_documents` — خزنة المستندات (Storage خاص + سياسات).
- `orphan_needs` — بنود الاحتياج (تعليم، صحة، غذاء، سكن) بمبلغ شهري لكل بند؛ مجموعها = المبلغ المقترح.
- `sponsorships` — عقد الكفالة (كافل، يتيم، نوع: شهري/مرة واحدة/جزئي، مبلغ، حالة، تواريخ).
- `sponsorship_payments` — كل دفعة، مرجع بوابة الدفع، الحالة، الإيصال.
- `disbursements` — الصرف من المنصة لجهة الرعاية + إثباتات.
- `progress_reports` — التقارير الدورية ومرفقاتها + حالة مراجعة الإدارة.
- `messages` / `notifications` / `timeline_events` / `audit_log` — منقولة من مهر كما هي.
- `user_roles` + `has_role()` — الأدوار في جدول منفصل (بلا أي دور على جدول البروفايل).
- `api_clients` / `api_import_jobs` / `external_profile_map` — تكامل API الداخلي (أدناه).

الخصوصية: البروفايل العام يعرض اسماً مختصراً/رمزاً، العمر، المنطقة، الاحتياج، ولا يعرض الصور الكاملة أو الوثائق. الحقول الحسّاسة تُقرأ فقط عبر RLS للإدارة والجهة الراعية وولي الأمر، والكافل يرى تفاصيل أوسع فقط بعد اعتماد كفالته.

## المطابقة (Matching)

دالة `suggest_orphans_for_sponsor` على نمط `suggest_jobs_for_applicant` في مهر: ترشيح حسب الميزانية الشهرية للكافل، المنطقة، الفئة العمرية، نوع الاحتياج، مع استبعاد المكفولين بالكامل والمرفوضين سابقاً، وترتيب حسب فجوة التمويل وأقدمية الانتظار.

## التكامل مع المنصات الداخلية عبر API

- **استيراد**: `POST /api/public/integrations/orphans/import` — HMAC للتوقيع + مفتاح عميل، Zod للتحقق، upsert عبر `external_ref` مع بقاء الملفات في حالة «قيد المراجعة» حتى اعتماد الإدارة.
- **تصدير/استعلام**: `GET /api/public/integrations/orphans` (حقول عامة فقط) و`GET .../sponsorships/:ref` لحالة الكفالة.
- **Webhooks صادرة** عند: اعتماد ملف، بدء كفالة، دفعة ناجحة، تقرير جديد.
- شاشة إدارة لمفاتيح العملاء وسجلّ مهام الاستيراد وأخطائها.

## الدفع الإلكتروني

بوابة دفع (careem افتراضياً؛ امكانية اضافة مزوّد  إن حدّدته) مع:

- دفعة لمرة واحدة + اشتراك شهري للكفالة، وإلغاء/إيقاف من لوحة الكافل.
- Webhook موقّع يحدّث `sponsorship_payments` ويشغّل الإشعارات.
- سجل مالي للإدارة: المحصّل، المصروف، الرصيد لكل يتيم/جهة.

## الشاشات

عام: الرئيسية، كيف تعمل الكفالة، دليل الأيتام (معتمد فقط)، صفحة يتيم عامة، الأسئلة، الخصوصية والشروط، تسجيل الدخول بالبريد فقط.
كافل: لوحة، كفالاتي، الدفعات والإيصالات، تقارير أيتامي، الرسائل.
جهة رعاية: أيتامي، إنشاء/تعديل ملف، المستندات، التقارير الدورية، الصرف.
ولي أمر: ملف اليتيم، الحالة، المستندات، الرسائل.
إدارة: نظرة عامة، طابور الاعتماد، الجهات، الكفالات، المالية والصرف، مراجعة التقارير، الرسائل، المراقبة والتنبيهات، المستخدمون والأدوار، تكاملات API.

## ما يُنقل من «مهر» كما هو

AppShell والتصميم العربي RTL، `_authenticated` gate، `rbac`، خزنة المستندات، الـStepper وحقول النماذج، الإشعارات والبريد المعاملاتي وقوالبه، لوحة المراقبة والتنبيهات وHMAC وrate limiting، SEO/head، sitemap، E2E.
ما يُحذف: منطق المهر/الوظائف/العروض/ساعات العمل/الرواتب/Calendly، والملفات الميتة (`store.ts`, `*View.tsx`).

## المراحل

1. **الأساس**: تفعيل Lovable Cloud، نقل الهيكل والتصميم والأدوار والمصادقة بالبريد + قشرة التطبيق والصفحات العامة.
2. **ملف اليتيم**: الجداول والـRLS والـGRANTs + نموذج 7 خطوات + المستندات + طابور اعتماد الإدارة.
3. **الدليل والمطابقة**: الدليل العام، صفحة اليتيم، دالة الترشيح، لوحة الكافل.
4. **الكفالة والدفع**: عقود الكفالة، بوابة الدفع، الاشتراك الشهري، الإيصالات، سجل الصرف.
5. **التقارير والمتابعة**: تقارير دورية من الجهة، مراجعة الإدارة، إشعارات الكافل، الخط الزمني.
6. **تكامل API**: مفاتيح العملاء، الاستيراد الموقّع، الاستعلام، الـwebhooks، شاشة الإدارة.
7. **التقوية والإطلاق**: rate limiting، تدقيق أمني وlinter، مراقبة، اختبارات E2E، SEO.

## تفاصيل تقنية

TanStack Start + createServerFn لكل منطق التطبيق، مسارات `/api/public/*` للتكاملات والـwebhooks والـcron فقط مع تحقق توقيع، Supabase مع RLS على كل جدول وGRANTs صريحة، الأدوار عبر `user_roles` + `has_role()` security definer، Storage خاص للوثائق مع روابط موقّعة، `supabaseAdmin` داخل الـhandlers فقط بعد التحقق من الدور.

كيف اضبط استدلال الايه انا وكافل اليتيم في الجنة كهاتين
