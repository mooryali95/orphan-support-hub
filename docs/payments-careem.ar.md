# بوابة الدفع — كريم: ما يلزم قبل البدء

**العملة المعتمدة: USD** (مؤكَّدة من المالك).

المرحلة 3 لا تبدأ قبل توفّر البنود المعلَّمة بـ🔴. البنود 🟡 تلزم قبل الإطلاق لا قبل البناء.

## 1. بيانات الحساب والاعتماد

| # | المطلوب | لماذا | الحالة |
|---|---|---|---|
| 🔴 | **رابط وثائق واجهة كريم للدفع** (أو اسم المنتج بدقّة: Careem Pay / Careem Business) | يحدّد شكل التكامل بالكامل؛ لكل منتج واجهة مختلفة | مطلوب |
| 🔴 | **معرّف التاجر** (Merchant ID / Account ID) | يُرسل مع كل طلب | مطلوب |
| 🔴 | **مفاتيح البيئة التجريبية** (Client ID + Secret أو API Key) | البناء والاختبار بلا أموال حقيقية | مطلوب |
| 🔴 | **سرّ توقيع الـwebhook** (Webhook Signing Secret) | بدونه لا يمكن التحقّق من صحة إشعار الدفع — وهذا ما يفعّل الكفالة | مطلوب |
| 🔴 | **عناوين الـAPI** للبيئتين التجريبية والإنتاجية | مطلوب |
| 🟡 | **مفاتيح الإنتاج** | تُضاف عند الإطلاق فقط، ولا تدخل المستودع أبداً | لاحقاً |
| 🟡 | **بطاقات الاختبار** في البيئة التجريبية | للتحقّق من مسارَي النجاح والفشل | مطلوب للاختبار |

## 2. أسئلة تقنية تُغيّر التصميم

| # | السؤال | لماذا يهم |
|---|---|---|
| 🔴 | **هل تدعم كريم الاشتراكات المتكرّرة (Recurring / Subscriptions)؟** | إن نعم: نُنشئ اشتراكاً لدى المزوّد ونخزّن `provider_subscription_id`. إن لا: نحفظ رمز البطاقة (token) ونحصّل شهرياً عبر cron. **مساران مختلفان تماماً في الكود.** |
| 🔴 | **هل يدعم حساب التاجر التحصيل بالـUSD؟** | كريم إقليمي وقد تكون التسوية بالدرهم أو الريال. إن اختلفت عملة العرض عن عملة التسوية نحتاج قراراً: نعرض USD ونحصّل بعملة أخرى بسعر صرف، أم نغيّر عملة العرض؟ |
| 🔴 | **ما أحداث الـwebhook المتاحة؟** (نجاح، فشل، استرداد، إلغاء اشتراك) | تحدّد انتقالات حالة الكفالة |
| 🟡 | **هل يوجد API للاسترداد (Refund)؟** | لازم لسياسة إلغاء الكفالة |
| 🟡 | **حدود المبالغ** (أدنى/أقصى للعملية) | يُضبط عليها تحقّق `zod` في `createSponsorship` |

## 3. ما تحتاج ضبطه أنت في لوحة كريم

1. **عناوين إعادة التوجيه (Redirect / Callback URLs)** — أضف نطاق المنصة إلى القائمة البيضاء:
   - `https://<النطاق>/api/payments/return`
   - `https://<النطاق>/api/payments/cancel`
2. **عنوان الـwebhook**: `https://<النطاق>/api/payments/webhook`
3. **تفعيل البيئة التجريبية** وإصدار مفاتيحها.

## 4. أين توضع الأسرار

**لا تضع أي مفتاح في `.env`** — الملف متتبَّع في Git ويُدفع إلى GitHub تلقائياً.

| المفتاح | المكان |
|---|---|
| `CAREEM_MERCHANT_ID` | `.env.local` أو متغيّرات بيئة Lovable Cloud |
| `CAREEM_API_KEY` / `CAREEM_CLIENT_SECRET` | نفسه |
| `CAREEM_WEBHOOK_SECRET` | نفسه |
| `SUPABASE_SERVICE_ROLE_KEY` | نفسه — يلزم لأن الـwebhook يكتب سجلّ المدفوعات متجاوزاً RLS |
| `LOVABLE_CRON_SECRET` | نفسه — يحمي مسار التحصيل الشهري |

انظر `.env.example` للقائمة الكاملة، و`docs/runbook.ar.md` لسياسة الأسرار.

## 5. ما هو جاهز فعلاً في المستودع

- `sponsorships.provider` و`provider_subscription_id` و`next_charge_at` — أعمدة جاهزة وفارغة.
- `sponsorship_payments` — الجدول جاهز، والكتابة عليه **محصورة في `service_role`** بعد إصلاح C3،
  فلا يستطيع العميل تلفيق قيد `paid`.
- حرّاس القاعدة يمنعون تفعيل أي كفالة من العميل؛ التفعيل من الـwebhook حصراً (C2).
- `src/integrations/supabase/cron-auth.ts` — التحقّق من سرّ الـcron جاهز وغير مستخدم بعد.

أي أن طبقة الأمان المالية مكتملة، والناقص هو التكامل نفسه.
