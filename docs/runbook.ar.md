# دليل التشغيل — كافل

## المدير المؤسّس

`p.o.m2012@hotmail.com` مسجَّل في `public.protected_admins` ويحمل دور `admin`
على الإنتاج. الحماية المطبَّقة:

| الحماية                          | الآلية                                                                                  |
| -------------------------------- | --------------------------------------------------------------------------------------- |
| لا يستطيع أحد إضافة نفسه للقائمة | `protected_admins` بلا `GRANT` وبلا سياسات — غير مرئية لـ`anon` و`authenticated`        |
| لا يمكن حذف الدور أو تخفيضه      | `trg_guard_protected_admin_role` على `user_roles`                                       |
| لا يمكن حذف الحساب               | `trg_guard_protected_admin_user` على `auth.users`                                       |
| لا يمكن إزالة آخر مدير           | نفس الحارس يرفض إذا بقي مدير واحد                                                       |
| استعادة تلقائية                  | لو حُذف الحساب بالتجاوز وأُعيد تسجيله بنفس البريد، يستعيد `admin` عبر `handle_new_user` |

الحماية **مطلقة حتى أمام `service_role`**. مخرج الطوارئ الوحيد إعلان صريح في
نفس الجلسة:

```sql
BEGIN;
SET LOCAL app.allow_protected_admin_change = 'yes-i-am-sure';
-- التعديل المطلوب هنا
COMMIT;
```

لإضافة مدير محميّ آخر:

```sql
INSERT INTO public.protected_admins (email, reason)
VALUES ('someone@example.com', 'سبب الحماية');
-- ثم امنح الدور للحساب القائم:
INSERT INTO public.user_roles (user_id, role)
SELECT id, 'admin' FROM auth.users WHERE lower(email) = 'someone@example.com'
ON CONFLICT DO NOTHING;
```

## إنشاء حساب مدير عادي (غير محميّ)

بعد إغلاق الثغرة **C1**، لم يعد أي مستخدم قادراً على منح نفسه دور `admin` عند
التسجيل. الأدوار القابلة للإسناد الذاتي هي `sponsor` و`care_org` فقط.

المدير يُسند يدوياً عبر `service_role` — من محرّر SQL في لوحة Supabase، أو
باتصال يحمل `SUPABASE_SERVICE_ROLE_KEY`:

```sql
-- 1) سجّل الحساب أولاً من واجهة /auth بالبريد المطلوب
-- 2) ثم امنحه الدور:
INSERT INTO public.user_roles (user_id, role)
SELECT id, 'admin' FROM auth.users WHERE email = 'admin@example.com'
ON CONFLICT DO NOTHING;
```

نفس الأمر ينطبق على دور `guardian` (ولي الأمر) حتى تُبنى لوحته في المرحلة 4.

## تدقيق لازم مرة واحدة بعد تطبيق الهجرة

إصلاح **C1** يمنع التصعيد الجديد، ولا يُزيل أي دور `admin` مُنح قبل الإصلاح.
راجع القائمة يدوياً واحذف ما لا تعرفه:

```sql
SELECT ur.user_id, u.email, ur.created_at
FROM public.user_roles ur
JOIN auth.users u ON u.id = ur.user_id
WHERE ur.role = 'admin'
ORDER BY ur.created_at;
```

راجع كذلك ما قد يكون نُشر أو فُعّل عبر الثغرات C2 و C4 و C5:

```sql
-- ملفات أيتام لا تتبع جهة رعاية، أو اعتُمدت بلا سجلّ مراجعة
SELECT id, code, display_name, status, org_id, created_by, approved_at
FROM public.orphans
WHERE org_id IS NULL OR (status = 'approved' AND approved_at IS NULL);

-- جهات معتمدة يملكها مستخدم (البيانات التجريبية بلا مالك)
SELECT id, name, status, owner_id FROM public.care_organizations
WHERE status = 'approved' AND owner_id IS NOT NULL;

-- كفالات نشطة بلا دفعة مسدّدة مقابلة
SELECT s.id, s.sponsor_id, s.orphan_id, s.amount, s.status
FROM public.sponsorships s
WHERE s.status = 'active'
  AND NOT EXISTS (
    SELECT 1 FROM public.sponsorship_payments p
    WHERE p.sponsorship_id = s.id AND p.status = 'paid'
  );
```

## نمط الحرّاس في القاعدة

الحرّاس المضافون في `20260823100000_phase0_critical_security_hardening.sql`
تتبع قاعدتين يجب الحفاظ عليهما عند أي تعديل لاحق:

1. **الدوال `SECURITY INVOKER` عمداً.** `SECURITY DEFINER` يبدّل `current_user`
   إلى مالك الدالة، فيمرّ شرط `current_user NOT IN ('authenticated','anon')`
   دائماً ويتعطّل الحارس بالكامل.
2. **`pg_trigger_depth() > 1` يسمح للمُشغّلات المتداخلة بالمرور** — وهو ما
   يُبقي `recalc_orphan_funding()` قادرة على تحديث `funded_monthly` رغم أن
   العمود محظور على العميل. لا يمكن للعميل انتحال هذا الشرط.

## صحّة التشغيل والتنبيه

ثمانية فحوصٍ تحسبها القاعدة (`ops_health` · الهجرة 0926)، وتظهر أعلى تبويب
«المراقبة» في لوحة الإدارة، غير السليم أوّلاً:

| الفحص                       | يصير                          | متى                                                |
| --------------------------- | ----------------------------- | -------------------------------------------------- |
| سلسلة سجلّ السلامة          | حرجاً                         | أي سطرٍ لا يطابق بصمته أو سابقه                    |
| أحداث الدفع                 | حرجاً                         | حدثٌ بخطأ، أو لم يُعالَج بعد ٣٠ دقيقة (آخر ٧ أيام) |
| الدفعات المعلّقة            | تنبيهاً                       | دفعةٌ معلّقة أكثر من ساعتين                        |
| التعارضات مع منصّات التشغيل | تنبيهاً، ثم حرجاً بعد ٧٢ ساعة | تعارضٌ مفتوح                                       |
| طلبات فكّ القفل             | تنبيهاً                       | طلبٌ ينتظر أكثر من ٤٨ ساعة                         |
| البريد                      | تنبيهاً                       | رسالةٌ استنفدت محاولاتها (آخر ٧ أيام)              |
| المزامنة                    | تنبيهاً                       | منصّةٌ فعّالة بلا دفعةٍ منذ ٤٨ ساعة                |
| النصاب                      | تنبيهاً                       | أقلّ من ثلاثة مشرفين                               |

**الجدولة:** `POST /api/ops/health` بترويسة `Authorization: Bearer $LOVABLE_CRON_SECRET`،
يومياً على الأقل (كل ساعة أفضل). كل تشغيلٍ يُسجَّل في `ops_runs` (إلحاقٌ فقط).

**التنبيه** إشعارٌ لكل مشرفٍ داخل التطبيق يسمّي العطل ويفتح تبويب المراقبة،
والبريد يتبعه من صندوق الإرسال ويحترم حجب البريد. لا يتكرّر في كل تشغيل:
يُرسل حين يتغيّر الحال، ومرّةً كل يومٍ ما دام غير سليم، ومرّةً عند العودة
إلى السلامة.

## الجدولة والمراقبة من الخارج (ARC-06)

التنبيه داخل المنصّة لا يُنبّه إن ماتت المنصّة أو مات المجدول. فثلاثة مراقبين
من خارجها، كلٌّ منها مجّانيٌّ في healthchecks.io أو Better Stack أو UptimeRobot:

| ما يُراقَب                | كيف                                                                                                            | المتغيّر                 | التنبيه                                 |
| ------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------ | --------------------------------------- |
| التطبيق يردّ والقاعدة تصل | مراقب HTTP كلّ ٥ دقائق: `GET /api/ops/health` بترويسة `Authorization: Bearer $LOVABLE_CRON_SECRET`، يتوقّع 200 | —                        | فشلان متتاليان                          |
| فحص الصحّة يجري           | المجدول يستدعي `POST /api/ops/health` كلّ ساعة؛ وهو ينقر النبض بعد كلّ تشغيل                                   | `HEARTBEAT_URL_OPS`      | لا نبض خلال ساعتين، أو نقرٌ على `/fail` |
| تصريف البريد يجري         | المجدول يستدعي `POST /api/notifications/dispatch` كلّ ٥ دقائق؛ ينقر النبض بعد كلّ تشغيل                        | `HEARTBEAT_URL_DISPATCH` | لا نبض خلال ٣٠ دقيقة، أو `/fail`        |

- **GET الصحّة** لا يُعيد إلا قيماً منطقية (`database`، `config_ok`، وحال كلّ ميزة:
  admin/cron/email/payments/grants) ومرجع الطلب عند الفشل؛ لا رسالة خطأٍ ولا اسم
  متغيّر. التفاصيل في سجلّ الخادم بالمرجع نفسه.
- **المسارات الثلاثة محدودة المعدّل** (دلو `cron`، ٣٠ في الدقيقة لكلّ عنوان)
  قبل فحص السرّ، وتُغلق إن تعذّر العدّ.
- **مسار البريد واحد:** `/api/notifications/dispatch` وزرّ الإدارة يناديان
  `src/lib/email-outbox.server.ts` نفسه: المطالبة من `claim_email_batch` (تعيد فحص
  إلغاء الاشتراك والأنواع المكتومة وحجب البريد لحظة الإرسال)، وقالب Lovable برابط
  الإلغاء. بلا `PUBLIC_BASE_URL` أو `LOVABLE_API_KEY` يتوقّف قبل المطالبة
  (`dispatch_runs.error = base_url_missing | email_unconfigured`) ولا يستهلك محاولات.

### السجلّ والأخطاء (ARC-05)

- كلّ فشلٍ في دالّة خادم (`{ ok: false }` أو استثناء)، وكلّ خطأٍ في المسارات،
  سطرُ JSON واحد في سجلّات Workers: `ts`، `level`، `event` (مثل
  `serverFn.setDonorMember`)، `request_id`، `code`، `sqlstate`، `message` الخام.
- المستخدم يرى رسالةً عربية و«المرجع: …» — وهو `request_id` نفسه، وفي ترويسة
  `x-request-id`. ابحث به في Workers Logs (Cloudflare ← Workers ← Logs) أو في مخزن
  Logpush.
- للتنبيه الفوري: `ERROR_REPORT_WEBHOOK_URL` (JSON بـPOST) أو `SENTRY_DSN`. بلاهما لا
  يُرسل شيء خارج سجلّات Workers.
- عند أوّل طلبٍ بعد كلّ نشر يُسجَّل `config.invalid` (خطأ) أو `config.features_off`
  (تحذير) بأسماء ما ينقص. راجعه بعد كلّ نشر.

## النسخ الاحتياطي والاستعادة (ARC-06)

**الهدف:** RPO ≤ ٢٤ ساعة الآن (النسخ اليومي)، و≤ ٥ دقائق متى فُعّل PITR. RTO ≤ ٤
ساعات لاستعادة القاعدة ونشر الواجهة.

1. **ما يحمله المزوّد.** القاعدة على Lovable Cloud (Supabase). النسخ اليومي متاحٌ
   في الخطط المدفوعة ويُحفظ ٧ أيام؛ والاستعادة لنقطةٍ زمنية (PITR) إضافةٌ مدفوعة.
   **تحقّق منهما الآن** في لوحة Supabase ← Database ← Backups، ودوّن الخطة ومدّة
   الحفظ هنا وفي سجلّ القرارات. إن لم يكن PITR مفعّلاً فـ RPO يوم كامل من الكفالات
   والمدفوعات: فعّله قبل فتح الدفع الإلكتروني.
2. **نسخةٌ مستقلّة أسبوعية** (لا تعتمد على المزوّد وحده):
   ```
   pg_dump "$PROD_DB_URL" --format=custom --no-owner --file=ioco-$(date -u +%F).dump
   ```
   تُشفَّر (`age` أو `gpg`) وتُحفظ خارج حساب Supabase، وتُحذف بعد ٩٠ يوماً
   (سياسة الاحتفاظ، `data_retention_policy`). فيها بيانات أطفال: لا تُرفع إلى مكانٍ
   مشترك، ولا تُفتح إلا على جهاز المؤسِّس أو قاعدة التمرين.
3. **الخزائن (Storage):** الصور والوثائق ليست في `pg_dump`. انسخ خزائن
   `orphan-photos` و`orphan-documents` و`org-documents` شهرياً بواجهة Storage أو
   `supabase storage cp -r`، بالتشفير نفسه.

### تمرين الاستعادة (كلّ ثلاثة أشهر، ودوّن نتيجته)

1. أنشئ مشروع Supabase مؤقّتاً (أو قاعدة Postgres 15+ محلّية).
2. `pg_restore --no-owner --dbname "$DRILL_DB_URL" ioco-<التاريخ>.dump`
   (أو استعد نسخة المزوّد إلى مشروعٍ جديد من لوحة Backups).
3. شغّل `supabase/release/00-check-applied.sql` ثم `03-smoke-test.sql`: كلّ سطرٍ
   `true`، وأحدث رقمٍ يطابق البثّ.
4. قارن الأعداد: `SELECT count(*) FROM orphans, sponsorships, sponsorship_payments,
integrity_log` مع البثّ، وتحقّق من سلسلة السلامة (`verify_integrity_chain()` إن
   وُجدت في نسختك).
5. سجّل: التاريخ، النسخة المستعادة، الزمن المستغرق (هو RTO الفعلي)، وما فشل.
   ثم احذف المشروع المؤقّت.

## الاستجابة للحوادث وخرق البيانات

**الأدوار:** قائد الحادث (المؤسِّس، أو من ينيبه كتابةً)، ومسؤول الاتصال، ومسؤول
التقنية. شخصٌ واحد قد يحمل الثلاثة، لكن تُسمّى الأدوار في بداية كلّ حادث.

1. **الاحتواء (الساعة الأولى):**
   - أوقف ما ينزف: الدفع من `platform_settings.payments_on_hold = true`، والبريد من
     `email_on_hold = true`، ومفتاح شريكٍ مسرَّب بالإبطال من الإدارة ← التكامل.
   - دوّر الأسرار المتأثّرة: `SUPABASE_SERVICE_ROLE_KEY` (لوحة Supabase ← API)،
     `LOVABLE_CRON_SECRET` (اضبط القديم في `LOVABLE_CRON_SECRET_PREVIOUS` حتى يُحدَّث
     المجدول)، `CREEM_*`، `GRANT_SIGNING_KEY`.
   - احفظ الأدلّة قبل أيّ إصلاح: سجلّات Workers للفترة، و`audit_log` و`integrity_log`
     (`COPY … TO STDOUT`)، ولقطة `pg_dump`.
2. **التقييم (خلال ٢٤ ساعة):** ما البيانات، وكم شخصاً، وهل فيها أطفال أو بيانات
   دفع، ومن أين دخل المهاجم. ابدأ بـ `request_id` من السجلّ وبـ `audit_log`.
3. **الإبلاغ — ٧٢ ساعة من العلم بالخرق** (GDPR م.٣٣، والقانون الألباني لحماية
   البيانات الشخصية رقم 124/2024 بالمهلة نفسها):
   - إلى هيئة حماية البيانات المختصّة (في ألبانيا: مفوّض الحق في المعلومات وحماية
     البيانات IDP؛ وفي الاتحاد الأوروبي: هيئة بلد الكافل المتأثّر). البلاغ يُرسل
     في المهلة حتى إن لم يكتمل التقييم، ثم يُستكمل.
   - إلى الأشخاص المتأثّرين دون تأخيرٍ إن كان الخطر عالياً — وبيانات طفلٍ أو موقعه
     خطرٌ عالٍ دائماً، ويُبلَّغ وليّه والجهة الراعية.
   - إلى مزوّد الدفع (Creem) إن مسّ الخرق بيانات الدفع.
   - سجّل كلّ خرقٍ ولو لم يُبلَّغ عنه (م.٣٣/٥): ماذا، ومتى، ولماذا لم يُبلَّغ.
4. **التعافي:** استعد من النسخة إن تلفت البيانات (القسم أعلاه)، وانشر الإصلاح عبر
   حزمة نشرٍ وسجّل رقمها.
5. **المراجعة (خلال أسبوعين):** ما الذي سمح به، وما الذي كشفه أو تأخّر في كشفه،
   وفحصٌ جديد في `supabase/tests/` يسقط إن عاد.

## الإصدار والرجوع عنه (ARC-13)

قبل كلّ حزمة نشر (`supabase/release/README.md`):

1. **علامة استعادة:** خذ نسخةً يدوية من لوحة Supabase ← Backups (أو دوّن الوقت
   بالثانية إن كان PITR مفعّلاً)، و`pg_dump --schema-only` للمقارنة بعدها.
2. **البروفة:** `scripts/release-rehearsal.sh` بالحزم بترتيب نشرها، ويجب أن تنجح.
3. **التطبيق** معاملةٌ واحدة: فشلُ سطرٍ يُرجع كلّ شيء، فلا رجوع لازم في هذه الحالة.

**إن نجحت الحزمة ثم ظهر عطل:**

- **الواجهة وحدها:** Lovable ← Publish ← اختر النشر السابق (History) وأعد نشره.
  الحزم كلّها متوافقةٌ مع الواجهة السابقة بنقصٍ آمن (انظر قسم كلّ إصدار).
- **القاعدة:** الهجرات لا تحمل `down`. فالرجوع **إلى الأمام**: هجرةٌ جديدة تُعيد
  الدالّة أو السياسة السابقة (نصّها في الهجرة التي سبقتها في المستودع)، بحزمةٍ
  وبروفةٍ كالمعتاد. وما لا يُصلح هكذا (بياناتٌ تلفت) يُستعاد من علامة الاستعادة إلى
